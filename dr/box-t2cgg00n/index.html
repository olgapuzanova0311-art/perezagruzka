# ИИ-офис с главным агентом в Telegram: пошаговая инструкция

Автор: Ольга Пузанова. Версия 2: ноябрь 2026 (отделы, сильные агенты, всё работает на подписке Claude без отдельного API-ключа).

Эта инструкция состоит из двух частей:
- **Часть А.** Что ты делаешь руками: заводишь аккаунты и получаешь ключи. Это 30-40 минут, программировать не нужно.
- **Часть Б.** Техническое задание для Claude Code. Загрузи этот файл в Claude Code и напиши: «Собери ИИ-офис по этой инструкции, часть Б. Ключи из части А я дам, когда спросишь». Дальше он соберёт всё сам и будет спрашивать тебя только про ключи.

```

        ▼

```

1. **ИИ-офис.** Веб-страница с пиксельным офисом из 8 комнат-отделов с табличками: Штаб, Маркетинг, Контент-студия, Продажи, Аналитика, Обучение, Технический отдел, Приёмная, плюс лаунж с кофе. За столами сидят агенты-роботы, у каждого своя роль и сильная инструкция под твой бизнес. Ты видишь, кто работает (счётчик отдела загорается зелёным), как оркестратор разносит задачи по столам, читаешь отчёты, нанимаешь и увольняешь агентов. Когда агента нанимают, сверху появляется плашка «Новый сотрудник», робот входит в дверь, а оркестратор идёт с ним знакомиться.
2. **Главный агент в Telegram.** Это Claude Code, который живёт на сервере. Ты пишешь или надиктовываешь ему голосовое. Простое он делает сам, большое раскладывает на части и раздаёт агентам офиса, потом присылает тебе один итог. # Часть А. Что сделать руками

Все ключи и пароли записывай в одну личную заметку. Никому их не отправляй и не публикуй.

### Шаг 1. Claude и Claude Code
1. Оформи подписку Claude Max на claude.ai.
2. Открой Claude Code: на сайте claude.ai/code, в приложении Claude для компьютера или в терминале. Подойдёт любой вариант.
3. Выпусти токен подписки для сервера. На компьютере в терминале выполни `claude setup-token` (если Claude Code в терминале не установлен: `npm install -g @anthropic-ai/claude-code`). Откроется браузер, подтверди вход, в терминале появится длинный токен. Сохрани его в заметку. Этот токен даёт серверу работать на твоей подписке, никому его не показывай.

### Шаг 2. GitHub
1. Зарегистрируйся на github.com.
2. Нажми **New repository**, назови `ii-office`, выбери **Private** и нажми **Create repository**.
3. Подключи GitHub к Claude Code. В claude.ai/code это кнопка подключения GitHub при создании сессии; выбери репозиторий `ii-office`.
4. Создай токен для главного агента, чтобы он сам публиковал изменения:
   github.com/settings/personal-access-tokens → **Generate new token** →
   - Token name: `ii-agent`, Expiration: 90 дней;
   - Repository access: **All repositories** (или только `ii-office`, если хочешь осторожнее);
   - Permissions → **Contents**, **Pull requests**, **Workflows**: Read and write; **Administration**: Read and write, если хочешь, чтобы агент сам создавал новые репозитории;
   - **Generate token** → сохрани `github_pat_...` в заметку.

### Шаг 3. Ключ Anthropic API (необязательно)
Пропусти этот шаг, если всё будет работать на подписке. Ключ нужен, только если хочешь, чтобы офис работал без подписки:
1. Зайди на console.anthropic.com, зарегистрируйся.
2. **Billing**: пополни баланс от $10 и поставь месячный лимит расходов (например $50).
3. **API Keys → Create Key**, назови `ii-office`, сохрани ключ `sk-ant-...` в заметку.

### Шаг 4. Railway
1. Зарегистрируйся на railway.com через GitHub.
2. Подключи тариф **Hobby**. На бесплатном пробном сервера засыпают, а агенту нужно работать круглосуточно.
3. Разреши Railway доступ к репозиторию: при первом создании проекта Railway попросит установить GitHub-приложение, выбери `ii-office`.
4. Создай токен: аватар справа сверху → **Account Settings → Tokens → Create Token**, назови `ii-agent`, сохрани в заметку.
5. Если Claude Code у тебя подключён к Railway через коннектор, он сможет создать сервисы сам. Если нет, он попросит токен из пункта 4 или подскажет, какие кнопки нажать.

### Шаг 5. Telegram-бот
1. В Telegram открой **@BotFather**, отправь `/newbot`.
2. Придумай имя (например «Мой ИИ-офис») и username, который заканчивается на `bot`.
3. Сохрани токен вида `123456789:AA...` в заметку.
4. Узнай свой Telegram id: напиши боту **@userinfobot**, он пришлёт число. Сохрани в заметку. Это нужно, чтобы бот отвечал только тебе.

### Шаг 6. Пароль офиса
Придумай пароль на вход в офис, 10+ символов, сохрани в заметку.

### Шаг 6а. Паспорт бизнеса
Напиши 5-10 строк о себе: кто ты и чем занимаешься, твои аудитории, продукты и цены, голос (как ты пишешь), чего нельзя обещать. Это контекст, который получит каждый агент. Без него агенты пишут общими словами.

### Шаг 7. Проверь заметку
У тебя должно быть 6 строк (седьмая по желанию) и паспорт бизнеса:

| Что | Где взяли | Как назовём переменную |
|---|---|---|
| Токен подписки Claude | шаг 1 | `CLAUDE_CODE_OAUTH_TOKEN` |
| Ключ Anthropic API (необязательно) | шаг 3 | `ANTHROPIC_API_KEY` |
| Токен Telegram-бота | шаг 5 | `TG_TOKEN` |
| Твой Telegram id | шаг 5 | `TG_OWNERS` |
| Пароль офиса | шаг 6 | `OFFICE_PASSWORD` |
| Токен GitHub | шаг 2 | `GH_TOKEN` |
| Токен Railway | шаг 4 | `RAILWAY_API_TOKEN` |

Готово. Открывай Claude Code в репозитории `ii-office`, загружай этот файл и пиши: **«Собери ИИ-офис по этой инструкции, часть Б»**.

## Б2. ИИ-офис (`office/`)

**Стек:** Python 3.12, aiohttp, SQLite (файл на томе `/data/office.db`). Модель по умолчанию `claude-opus-5-5` (переменная `CLAUDE_MODEL`). Сверь актуальные id моделей по документации Anthropic перед написанием кода.

**Мозг агентов (две дорожки):**
1. **Подписка (основная).** Офис отправляет запрос сервису `agent` по внутренней сети Railway: `POST http://agent.railway.internal:8080/office-llm {secret, system, messages, model}`. `secret` = HMAC-SHA256 от `OFFICE_PASSWORD` с сообщением `office-llm`, один и тот же на обоих сервисах. Агент запускает `claude -p "<переписка>" --output-format json --model <модель> --append-system-prompt "<инструкция агента>" --tools ""` в пустой папке и возвращает `{text}` или `{error}`. Не больше 3 запусков одновременно, таймаут 15 минут. Переменная офиса `SUBSCRIPTION_URL` (пустая отключает).
2. **API-ключ (запасная).** Если подписка недоступна и задан `ANTHROPIC_API_KEY`, официальный SDK `anthropic` (AsyncAnthropic). Ошибки API и `stop_reason == "refusal"` показывать понятным сообщением в чате офиса, в том числе «закончился баланс».

В шапке офиса показывай, на чём работает мозг: «claude-opus-5-5 · подписка».

**Переменные:** `OFFICE_PASSWORD`, `DB_PATH=/data/office.db`, `PORT`, необязательно `ANTHROPIC_API_KEY`, `SUBSCRIPTION_URL`.

**Таблицы:**
- `agents(id, name, role, color, prompt, model, is_main, status, dept, created)`;
- `messages(id, agent_id, role, author, text, ts)`;
- `tasks(id, agent_id, title, status, result, from_agent, created, updated)`;
- `events(id, type, a, b, text, ts)`;
- `settings(k, v)`. Каждое обновление состава и инструкций команды делай миграцией с флагом в `settings` (`team_v1`, `depts_v1`…), чтобы она прошла один раз и не затёрла правки владельца.

**Отделы (`departments.py`)**: ключ, название, чем занимается. Порядок задаёт расположение комнат:

| Ключ | Отдел | Агенты на старте |
|---|---|---|
| `lead` | Штаб | **AI-оркестратор** (главный), операционный директор, продуктовый стратег |
| `marketing` | Маркетинг | трендхантер, таргетолог, копирайтер |
| `studio` | Контент-студия | контент-продюсер, сценарист рилс, дизайнер, монтажёр, моушн-дизайнер |
| `sales` | Продажи | продажник (скрипты, возражения, дожимы), воронщик (автоворонки в ботах) |
| `analytics` | Аналитика | аналитик (метрики, юнит-экономика, узкое место), исследователь рынка |
| `edu` | Обучение | методолог, куратор (проверка ДЗ, ответы ученикам) |
| `tech` | Технический отдел | архитектор внедрений, вайбкодер (сайты и боты словами), промпт-инженер |
| `reception` | Приёмная | ассистент (почта и срочное), тайм-менеджер |

Подстрой состав под нишу владельца: спроси, какие отделы ему нужны.

**Сильный агент = 4 части промпта:**
1. Роль и что приходит на вход.
2. Метод по шагам. Пример для таргетолога: цель → 3-5 гипотез «сегмент × боль × оффер» → аудитории → по 3 текста объявления → бюджет и стоп-метрика на гипотезу → что масштабировать.
3. Точный формат результата («таблица гипотез, тексты объявлений, медиаплан»).
4. Общие блоки, которые код добавляет каждому агенту: **контекст бизнеса** (паспорт из шага 6а: кто владелец, аудитории, продукты и цены, ядро смыслов, язык клиента, что нельзя обещать) и **проверка перед сдачей** («результат можно сразу использовать; цифры и конкретика; всё непроверенное помечено «проверить»; в конце 1-3 пункта, что нужно от владельца»). Плюс правила голоса владельца.

**Оркестратор** раздаёт работу команде. Сам отвечает только на вопросы и уточнения, любую рабочую задачу (текст, сценарий, план, исследование, разбор) отдаёт 1-3 агентам по их ролям. Иначе он делает всё сам, и офис стоит: в первой версии так и было. В его системную инструкцию код подставляет команду, сгруппированную по отделам.

**Делегирование:**
- главный поручает задачу отдельной строкой `@Имя агента: задача` (агенты не видят переписку, всё нужное кладётся в задачу);
- код находит такие строки, создаёт задачи и событие `talk`, агенты работают параллельно, не больше 3 запросов одновременно;
- отчёты падают в чат главного, после всех отчётов главный один раз сводит итог без новых поручений;
- строка `НАНЯТЬ: Имя | роль | инструкция` нанимает агента. Отдел подбирается по ключевым словам роли (рилс, монтаж → студия; реклама, таргет → маркетинг; продажи, воронка → продажи и так далее), иначе агент садится в лаунж.

**API (всё кроме `/`, `/health`, `/api/login` закрыто паролем через cookie):**
- `GET /`: страница офиса; `GET /health`: `ok`;
- `POST /api/login {password}`: cookie на 90 дней;
- `GET /api/state?since=<event_id>`: агенты (с `dept`), список отделов, последние 40 задач, новые события, на чём работает мозг;
- `GET /api/messages?agent_id=`: последние 60 сообщений; длинные отчёты в чате обрезай до ~2500 символов, целиком они во вкладке «Задачи»;
- `POST /api/chat {agent_id, text}`, `POST /api/tasks {agent_id, title, from_main?, external?}`, `POST /api/tasks/{id}/done {result, error?}`;
- `POST /api/agents` (нанять или изменить, поле `dept`), `DELETE /api/agents/{id}` (главного нельзя);
- `GET /api/templates`: готовые роли всех отделов для найма в один клик.

**Лёгкость:** страница опрашивает `/api/state` каждые 1,5 секунды, поэтому отдавай JSON без экранирования кириллицы (`ensure_ascii=False`) и обрезай заголовки задач в `state` до 400 символов. Без этого офис тянул 1,3 МБ каждые полторы секунды и тормозил.

**Страница `index.html`** (один файл, без сборки):
- **Офис.** Холст 512×320 логических пикселей, масштаб под размер, `image-rendering: pixelated`. Сверху окна с вечерним городом. Ниже сетка 3×3: 8 комнат-отделов и лаунж (диван, кофемашина). В каждой комнате 4 стола в ряд, у штаба доска с графиком. Пол каждой комнаты своего оттенка.
- **Таблички отделов** рисуются поверх холста в полном разрешении: иконка, название, число агентов. Число жёлтое, зелёное, если кто-то в отделе работает.
- **Рассадка.** Агент садится за свободный стол своего отдела, кому не хватило, идёт в лаунж.
- **Роботы.** Свой цвет и антенна, у главного корона, подпись имени без «AI-». В статусе «работает» на мониторе бегут строчки. В основном сидят у себя, иногда ходят за кофе. Событие `talk`: робот обходит адресатов по очереди с пузырём «📋 несу задачу», возвращается на место.
- **Найм.** Событие `hire`: жёлтая плашка «🧑‍💼 Новый сотрудник: имя» и роль, новый робот появляется у входа и здоровается, главный идёт к нему «🤝 Добро пожаловать в команду!», карточка в ленте команды мигает.
- **Шапка:** логотип, на чём работает мозг, «N в работе · M свободны · 8 отделов», кнопки «Задачи» и «+ Нанять агента».
- **Лента команды** под офисом: карточки по отделам, у каждой статус и отдел.
- **Правая панель:** вкладки «Чат», «Задачи», «Настройки»; окно найма с готовыми ролями и выбором отдела.
- **Первая загрузка** проигрывает последние 20 событий, чтобы было видно, как раздавались задачи.
- **Мобильная версия.** Офис сверху, панель снизу, страница не шире экрана (у сетки `minmax(0,1fr)`, у длинных подписей `min-width: 0`).

## Б3. Главный агент в Telegram (`agent/`)

**Dockerfile** (сборка из корня репозитория, чтобы внутри были все файлы проекта):
- база: `python:3.12-slim`;
- пакеты apt: `curl git ripgrep ca-certificates gnupg ffmpeg fontconfig fonts-dejavu-core build-essential cmake chromium`;
- Node.js 22 (репозиторий nodesource), `gh` (официальный репозиторий GitHub CLI);
- через npm глобально: `@anthropic-ai/claude-code` и `@railway/cli`;
- шрифты Montserrat, Oswald, Manrope с github.com/google/fonts в `/usr/share/fonts/truetype/brand`, потом `fc-cache -f`;
- `pip install aiohttp faster-whisper tzdata`;
- `COPY . /app/repo`, пользователь `agent` (uid 1000). Claude Code не включает режим без подтверждений под root, поэтому запускаем под обычным пользователем;
- `CMD`: создать `/data`, `chown agent /data`, `runuser -u agent -- python /app/repo/agent/bot.py`;
- `ENV REMOTION_CHROME_EXECUTABLE=/usr/bin/chromium`.

**Переменные:**
- `TG_TOKEN`, `TG_OWNERS` (id владельца);
- `CLAUDE_CODE_OAUTH_TOKEN` (токен подписки из шага 1; Claude Code на сервере работает на подписке владельца), `MODEL=claude-opus-5-5`;
- `OFFICE_URL` (адрес офиса), `OFFICE_PASSWORD`;
- `WHISPER_MODEL=small`;
- `GH_TOKEN`, `RAILWAY_API_TOKEN`;
- `RAILWAY_DOCKERFILE_PATH=agent/Dockerfile`.

**bot.py, поведение:**

1. **При старте:**
   - копирует файлы репозитория в рабочую папку `/data/ws` (новые файлы и более свежие версии, правки агента не затирать);
   - `agent/skills` копирует в `/data/ws/.claude/skills`, создаёт папки `inbox/`, `outbox/`, `work/`;
   - ставит `HOME=/data/home`, чтобы память и сессии Claude Code жили на томе;
   - если есть `GH_TOKEN`: `gh auth setup-git` и имя автора коммитов;
   - поднимает веб-сервер на `::` (IPv4 и IPv6, иначе офис не достучится по внутренней сети Railway): `/` с ответом `ok` для проверки здоровья и `POST /office-llm` (мозг агентов офиса на подписке, см. Б2: проверка `secret`, `claude -p … --tools ""` в пустой папке `/data/office-llm`, не больше 3 одновременно);
   - в фоне загружает модель Whisper.
2. **Telegram:** long polling (`getUpdates`, timeout 50). Сначала `deleteWebhook`, потом `setMyCommands`: `/new`, `/stop`, `/office`.
3. **Доступ.** Отвечает только id из `TG_OWNERS` и тем, кто прислал `/start <пароль офиса>`. Их id сохраняются в `/data/state.json`.
4. **Голосовые, аудио, кружки:**
   - скачивает файл, декодирует через ffmpeg в 16 кГц моно и передаёт массив в faster-whisper (`language='ru'`, `vad_filter=True`, `compute_type='int8'`);
   - **важно:** файл в Whisper напрямую не передавать, новые версии PyAV падают с ошибкой `metadata_errors`;
   - сначала присылает расшифровку «🎙 …», потом работает.
5. **Фото и документы** сохраняет в `inbox/` и передаёт путь в задачу. Пересланные сообщения помечает, от кого они. Telegram отдаёт ботам файлы только до 20 МБ, большие видео пусть присылают ссылкой.
6. **Запуск Claude Code** в `/data/ws`:
   `claude -p "<сообщение>" --output-format stream-json --verbose --model $MODEL --permission-mode bypassPermissions --append-system-prompt "<SYSTEM>" [--resume <session_id>]`
   - id сессии хранится на каждый чат, чтобы разговор продолжался;
   - одна задача за раз на чат, остальные в очередь;
   - пока идёт работа, бот редактирует одно сообщение «⏳ Работаю» и пишет последние шаги понятными словами («📖 читаю…», «🏢 поручаю: …»);
   - итог отправляет кусками до 4000 символов без markdown;
   - потом отправляет файлы, которые появились в `outbox/` за время задачи (видео, фото, документы до 50 МБ).
7. **Команды:** `/new` начинает новую сессию, `/stop` останавливает процесс, `/office` присылает ссылку на офис.
8. **SYSTEM**, системная инструкция главного агента, содержит:
   - кто владелец и что в начале разговора нужно прочитать `agent/MEMORY.md` и дописывать туда новые факты;
   - простое делать самому, большое раскладывать и поручать офису через `python agent/office.py` (`team`, `task "Имя" "задача"`, `wait <id>`, `tasks`, `hire`);
   - что агенты офиса не видят переписку, поэтому в задачу кладётся весь контекст;
   - про завод агентов (ниже);
   - про `inbox/` и `outbox/`, про навыки монтажа, сайтов и публикации;
   - формат ответов для Telegram;
   - запреты: не удалять сервисы, данные и репозитории без прямой просьбы, не публиковать ключи.

**office.py:** вход в офис по паролю, команды `team`, `task` (с `from_main: true`), `wait` (опрос до готовности, максимум 15 минут, печать отчётов), `tasks`, `hire`.

**Завод агентов (`tools/factory.py` + цикл в bot.py):**
- `create <id> --name --role --prompt-file [--skills] [--tools] [--model]`:
  - пишет субагента `.claude/agents/<id>.md` (frontmatter `name`, `description`, `tools`, `model`; тело: инструкция, список навыков, «голос владельца, outbox/, итог в конце»);
  - проверяет, что навыки существуют;
  - нанимает робота в офис и пишет реестр `/data/factory.json`;
- `list`, `schedule <id> "<cron>" "задача"`, `unschedule`, `run <id> "задача"` (кладёт задание в `/data/factory-queue/`), `delete`;
- **цикл в bot.py** каждые 15 секунд:
  - забирает задания из очереди и раз в минуту проверяет cron по Москве (поддержка `*`, списков, диапазонов, шагов `*/n`, воскресенье 0 и 7);
  - запускает `claude -p <задача> --output-format json --append-system-prompt <тело агента>` с моделью агента;
  - перед запуском ставит внешнюю задачу в офис, после запуска закрывает её отчётом;
  - присылает владельцу «🤖 Имя · по расписанию» с итогом и файлами;
  - один и тот же агент не запускается дважды одновременно;
- в SYSTEM записать порядок сборки агента:
  1. продумать роль;
  2. написать инструкцию в `work/<id>.md`;
  3. при необходимости создать навык;
  4. `create`;
  5. пробный `run`;
  6. `schedule`;
- правило: не чаще раза в час без прямой просьбы, каждый запуск тратит деньги.

**Навыки главного агента (`agent/skills/<навык>/SKILL.md`, frontmatter `name`, `description`):**
- `site-builder`:
  - сайт одним HTML-файлом;
  - адаптив 360-1440 px;
  - проверка скриншотами `chromium --headless --no-sandbox --window-size=390,844 --screenshot=...` и 1440×900 с исправлением найденного;
  - отдача в `outbox/` или публикация.
- `publish`:
  - новый проект: `gh repo create <аккаунт>/<имя> --private --source . --push`;
  - Railway: `railway init`, `railway up --detach`, `railway domain`, проверка `curl -sI` и логи сборки при ошибке;
  - существующие сервисы обновляются пушем в ветку;
  - удалять ничего нельзя без прямой просьбы.
- `montage`:
  - ffmpeg: вертикаль 9:16 с обрезкой или размытым фоном, нарезка;
  - вырезание пауз по таймингам слов из `tools/subs.py silences`;
  - субтитры ASS с подсветкой текущего слова (`tools/subs.py ass`);
  - музыка с приглушением, текст-хук, обложка;
  - проверка кадром, отдача в `outbox/` до 50 МБ.
- Маркетинговые и дизайнерские навыки, которые есть у владельца в Claude, можно скопировать в `agent/skills`, если у них открытая лицензия (MIT или Apache). Лицензию положи рядом.

**MEMORY.md:** кто владелец, ниша, аудитория, голос, проекты и ссылки, какие доступы подключены. Без паролей и ключей.

## Б4. Публикация на Railway

1. Создай проект Railway, например `ii-office`, через коннектор Railway, CLI с токеном владельца или по шагам для владельца.
2. **Сервис `office`:**
   - источник: репозиторий, ветка `main`;
   - Root Directory `/office`;
   - Start Command `python main.py`;
   - Healthcheck `/health`;
   - том `/data`;
   - переменные `OFFICE_PASSWORD`, `DB_PATH=/data/office.db`, по желанию `ANTHROPIC_API_KEY` как запасной мозг;
   - **Generate Domain**: это адрес офиса.
3. **Сервис `agent`:**
   - тот же репозиторий, Root Directory пустой;
   - `RAILWAY_DOCKERFILE_PATH=agent/Dockerfile`;
   - том `/data`;
   - Restart Policy: Always;
   - все переменные из Б3, `OFFICE_URL` = домен офиса;
   - Watch Paths: `agent/**`, чтобы правки офиса не перезапускали бота;
   - внутреннее имя сервиса `agent`: офис ходит к нему по адресу `agent.railway.internal:8080` (Private Networking включён в проекте по умолчанию).
4. Дождись зелёного статуса обоих сервисов и проверь логи.
5. Важно: у бота должен быть **один** работающий экземпляр. Два экземпляра с одним токеном дают ошибку Telegram 409 Conflict.

| Что видишь | Почему | Что сделать |
|---|---|---|
| Бот молчит | сервис `agent` упал или перезапускается | Railway → agent → Deployments → логи; попроси Claude Code починить |

Библиотека сцен (каждая отдельный компонент):

counter: счётчик цифр; list: пункты появляются по одному; compare: было/стало со шторкой;
prompt: карточка промпта, текст печатается; screen: скрин сайта в рамке телефона с прокруткой;
photo: моё фото в трёх раскладках (full: наезд со вспышкой; card: карточка в белой рамке с поворотом;

### Площадка

Маркетплейс: [Ozon / Wildberries / оба с переключателем].

### Источник данных: загрузка отчётов

Загрузка одного или нескольких файлов финансового отчёта, отчёта по продажам/остаткам и отчёта по рекламе (формат [.xlsx, экспорт из личного кабинета Ozon / Wildberries]). Парсинг через SheetJS (xlsx.full.min.js с cdnjs).

К этому сообщению приложены реальные файлы отчётов - финансовый отчёт, отчёт по продажам и отчёт по рекламе. Изучи их структуру (названия листов, реальные заголовки колонок, в какой именно строке они находятся, единицы измерения, формат чисел и дат) и построй парсер именно под неё, а не под общий шаблон того, как «обычно» выглядит выгрузка площадки. Если файлы к сообщению не приложены - не достраивай структуру по догадке: сначала явно попроси меня прислать файлы или как минимум точные названия листов и заголовков колонок (включая случай двухстрочных или объединённых заголовков) и 3-5 строк примера данных по каждому типу отчёта, и только после этого пиши парсер.

Учитывай типичные особенности реальных выгрузок маркетплейсов, а не только «чистого» табличного формата:
- заголовок таблицы может быть не в первой строке листа - определяй строку заголовка по совпадению с ожидаемым набором ключевых слов, а не жёстко бери строку 1
- в шапке бывают объединённые ячейки - если название колонки пустое из-за объединения, наследуй его от ближайшей заполненной ячейки слева или в предыдущей строке
- числа могут быть с запятой как разделителем дробной части, с неразрывным пробелом как разделителем тысяч и с символом валюты - приводи к числу единообразно
- даты могут прийти как серийный номер Excel или как текстовая строка в разных форматах - нормализуй оба варианта

Если структура разных отчётов не совпадает по колонкам, учти это отдельными правилами парсинга для каждого типа файла и определяй тип файла автоматически по набору колонок или названию листа, а не по имени файла. Если тип файла не удаётся определить с уверенностью (совпало меньше половины ожидаемых ключевых колонок) - не гадай: покажи пользователю обнаруженные названия листов и колонок и дай выбрать тип файла вручную из списка, вместо того чтобы молча классифицировать неправильно.

После каждой успешной загрузки файла показывай короткий отчёт о результате парсинга: определённый тип отчёта, определённый период (диапазон дат), количество распознанных строк, и отдельно - список ожидаемых колонок, которые не удалось найти. Это должно быть видно сразу после загрузки, а не обнаруживаться позже как «непонятно откуда нули».

Если парсер не находит обязательную колонку - показывай понятную ошибку с указанием, какая именно колонка не найдена и в каком файле, а не падай молча и не подставляй нули вместо неё.

Если пользователь загружает несколько файлов за разные периоды, дашборд должен объединять их и давать выбор периода для отображения.

**Пересчёт при новых загрузках.** Загрузка новых файлов (в том числе повторная загрузка отчёта за уже существующий период или добавление отчёта за новый период) должна автоматически запускать полный пересчёт всех метрик, графиков, автовыводов и таблиц - без перезагрузки страницы и без ручных действий пользователя. Если новый файл перекрывает по датам уже загруженный, дай пользователю явный выбор: заменить старые данные новыми за этот период или объединить (например, если один файл - черновая выгрузка, а второй - обновлённая за тот же период). Ранее введённая вручную себестоимость и настройки при пересчёте не должны сбрасываться - они должны заново примениться к обновлённому набору данных по тем же SKU.

### Себестоимость: логика определения источника

Себестоимость товара в отчётах площадки чаще всего отсутствует, но иногда встречается (например, если продавец сам выгружает управленческий отчёт с колонкой себестоимости). Поэтому логика должна быть такой:

1. При парсинге каждого отчёта явно проверяй, есть ли колонка с себестоимостью (по названию и по здравому смыслу - например, «закупочная цена», «себестоимость», «cost»). Если колонка найдена - используй эти значения и пометь их в интерфейсе как «из отчёта».
2. Если по какому-то SKU себестоимость не нашлась ни в одном из загруженных файлов - не показывай прибыль по этому товару как ноль или как приблизительную. Вместо этого явно предложи пользователю ввести себестоимость руками (поле ввода рядом с товаром), и пока она не введена - показывай статус «нет данных о себестоимости» вместо прибыли, ROI и маржи по этому товару, а не 0 или прочерк без пояснения.
3. Введённая вручную себестоимость помечается в интерфейсе как «вручную» (в отличие от «из отчёта»), сохраняется в браузере (localStorage) и подтягивается автоматически при следующих визитах и при загрузке новых отчётов по тому же SKU.
4. На уровне KPI-строки и общих итогов явно показывай, по какой доле выручки/товаров себестоимость известна (из отчёта + вручную), а по какой - нет, чтобы пользователь понимал, насколько цифрам прибыли можно доверять на текущий момент.

Это не частный случай только для себестоимости, а сквозной принцип «нет данных ≠ ноль», который действует для любой метрики во всём дашборде: если поле не найдено ни в одном файле или не может быть вычислено - везде показывай явный статус «нет данных» с пояснением, какого отчёта или колонки не хватает, а не 0, пустую ячейку или прочерк без объяснения. Нигде в коде не должно быть паттерна вида `значение || 0` для полей, пришедших из отчёта, - это маскирует реальное отсутствие данных как настоящий ноль.

### Формулы (единый источник истины)

Прежде чем писать интерфейс, зафиксируй расчёты в одном месте кода (один модуль/набор функций), и используй только эти функции во всех вкладках - ни в коем случае не дублируй реализацию одной и той же формулы в разных местах (KPI-строка, вотерфолл, юнит-экономика, таблица товаров должны считать через одни и те же функции):

- Прибыль = Выручка − Себестоимость − Эквайринг − Логистика − Хранение − Реклама на единицу − Комиссия площадки − Налоги − Возвраты/штрафы − Прочие удержания. Если какая-то из статей расходов не найдена ни в одном загруженном отчёте - исключай её из вычитаемых, но явно показывай в интерфейсе список статей, которые не учтены, а не молча считай их нулевыми
- Маржа % = Прибыль ÷ Выручка × 100
- ROI % = Прибыль ÷ Себестоимость × 100
- ДРР % = Расход на рекламу ÷ Выручка × 100
- Скорость продаж = среднее количество продаж в день за выбранный период
- Дней до обнуления остатка = Остаток ÷ Скорость продаж

**KPI-строка вверху** (видна на любой вкладке): выручка, себестоимость (% от выручки, с пометкой какая доля известна из отчёта/введена вручную/отсутствует), чистая прибыль (с пометкой «операционно прибыльно» / «операционный убыток»), маржинальность и ROI, расход на рекламу и общий ДРР, количество товаров, требующих внимания (сумма критичных по остаткам и убыточных).

**Обзор**

Блок автоматических текстовых выводов по периоду (не просто цифры, а готовые фразы): сколько товаров продаются в убыток и на какую сумму, у какой категории лучшая и у какой худшая маржа, сколько товаров закончится меньше чем через N дней, ДРР каталога относительно ориентира 7-15% с пояснением выше он или ниже нормы, сколько найдено точек роста в воронке и на какую сумму потенциальной прибыли, сколько товаров одновременно в группе C по выручке и при этом убыточны (кандидаты на вывод из ассортимента).

Нитка прибыли (waterfall-график): выручка → минус себестоимость → минус комиссии площадки/реклама/прочие удержания → чистая прибыль.

**План-факт**

Пользователь вручную задаёт план на месяц: плановая выручка и плановая прибыль (план по количеству продаж считается автоматически как план выручки, делённый на среднюю цену продажи по факту). Значения плана вводятся через интерфейс и сохраняются в браузере. Дополнительно можно задать план отдельно по каждой категории. Прогресс-бар по каждому показателю должен учитывать не просто факт/план, а темп: отметка на баре показывает ожидаемый процент выполнения на сегодняшний день месяца (например, если прошло 60% дней месяца, ожидается 60% выполнения), и явно подсвечивается, идёт ли пользователь по графику, немного отстаёт или сильно отстаёт. Отдельный блок «нужный темп»: текущая средняя выручка в день по загруженным данным, и сколько нужно зарабатывать в день до конца месяца, чтобы выполнить план, с явным сравнением этих двух цифр. Обработай случай, когда план задан на один месяц, а загруженные отчёты - за другой (например, план уже стоит на новый месяц, а данные ещё за старый): в этом случае прогресс не может считаться от факта, и это должно быть понятно из интерфейса, а не выглядеть как обнулившийся план.

**Юнит-экономика (новая вкладка)**

Отдельная вкладка, показывающая реальную фактическую юнит-экономику - и по каждому SKU, и агрегированно по каталогу/категории.

- Себестоимость по товару берётся по логике из раздела «Себестоимость: логика определения источника» выше: если найдена в отчёте - подтягивается автоматически, если нет - вводится вручную прямо на этой вкладке (поле ввода в строке товара), с сохранением в браузере и явной пометкой источника («из отчёта» / «вручную» / «не заполнено»).
- По каждому SKU показывай полную цепочку от цены до итоговой прибыли на единицу: цена продажи → себестоимость → эквайринг → логистика → хранение → реклама на единицу (расход на рекламу по SKU, делённый на количество продаж) → комиссия площадки → налоги → возвраты и штрафы на единицу → чистая прибыль на единицу → маржа в % → ROI на единицу.
- Товары без заполненной себестоимости выносятся в отдельный блок «нет данных о себестоимости» с прямой ссылкой на поле ввода, а не смешиваются с товарами, где юнитка посчитана полностью - чтобы пользователь сразу видел, что нужно доввести.
- Сортировка и фильтр по всем колонкам, поиск по названию/артикулу, фильтр по категории и по статусу заполненности себестоимости (из отчёта / вручную / не заполнено).
- Агрегированная сводка вверху вкладки: средняя маржа по каталогу, средний ROI, доля товаров с положительной юнит-экономикой, доля товаров, где юнитка ещё не может быть посчитана из-за отсутствующей себестоимости.
- Данные на этой вкладке пересчитываются автоматически при загрузке новых отчётов и при любом изменении вручную введённой себестоимости - без перезагрузки страницы.

**Товары**

Таблица по SKU с сортировкой по каждой колонке, поиском по названию/артикулу и фильтром по категории. По каждому товару, насколько позволяют загруженные отчёты: себестоимость за штуку (см. логику выше про источник и ручной ввод), цена, количество продаж, выручка, отдельными статьями - эквайринг, логистика, хранение, расход на рекламу, ДРР, налоги, штрафы, сумма возвратов, прочие удержания, итоговая чистая прибыль в рублях и на единицу, ROI, маржа в процентах, доля товара в общей выручке. ABC-метка отдельно по вкладу в прибыль и отдельно по вкладу в выручку - это два разных среза, их нельзя схлопывать в один. При клике на товар - разворачивающаяся детализация: нитка прибыли по этому товару, мини-воронка (показы → визиты в карточку → в корзину → заказано → доставлено, если такие данные есть в отчётах), остаток и скорость продаж, рекомендация по поставке.

**Реклама / Воронка**

Воронка всего каталога: показы → визиты в карточку → добавления в корзину → заказано (по данным из отчёта по рекламе и отчёта по продажам). Автоматический поиск точек роста по методу отклонения от медианы каталога: карточки с конверсией показ→корзина заметно ниже медианной при хорошей марже (слабая карточка), карточки с показами заметно ниже медианных при хорошей марже (недостаточно продвижения), карточки с высоким процентом брошенных корзин (конверсия корзина→заказ ниже медианной), карточки с низким процентом выкупа. По каждому найденному сигналу - оценка потенциального прироста прибыли (на основе медианной конверсии каталога и прибыли на единицу товара), с явной оговоркой, что это ориентир для приоритизации, а не гарантированная цифра. Отдельно - таблица расходов по рекламным кампаниям с ДРР и CTR, если в отчёте есть разбивка по кампаниям. Если файл отчёта по рекламе не удалось распознать или в нём не нашлись нужные колонки - вся вкладка должна явно показывать, каких данных не хватает, а не оставаться пустой без объяснений.

**Остатки**

KPI-блок: сколько товаров критично (меньше 7 дней), сколько требуют внимания (меньше 14 дней), сколько в норме - пороги должны быть настраиваемыми, а не жёстко зашитыми. Гистограмма распределения товаров по срокам до обнуления (до 7 дней, 7-14, 14-30, 30-60, больше 60). Список ближайших к обнулению товаров с датой предполагаемого обнуления. Таблица планирования по каждому SKU: остаток, скорость продаж в штуках в день (на основе истории продаж за период), сколько дней хватит остатка, статус, рекомендация по поставке (если явных данных для рекомендации недостаточно, дать простое правило: например, если дней хватит меньше 14 и товар не в группе C по прибыли - «пора поставлять»).

Если каких-то данных не хватает в загруженных файлах, соответствующий блок, колонка или расчёт должны корректно скрываться либо показывать заглушку с пояснением, какого именно отчёта или поля не хватает, а не падать с ошибкой и не показывать нули как будто это реальные данные.

### Сохранение состояния

Данные всех загруженных отчётов, введённая пользователем себестоимость по SKU (с пометкой источника), план на месяц и настройки порогов остатков сохраняются в браузере между визитами (localStorage), при повторном открытии файла ничего не нужно вводить заново.

Кнопка «сохранить срез» вручную сохраняет текущие ключевые показатели периода (выручка, прибыль, маржа, ДРР) с меткой времени - это и есть история для графика тренда на вкладке «Обзор». Явно объясни в интерфейсе, что график тренда наполняется только по мере того, как пользователь делает срезы, а не сам по себе.

### Технические требования

- Один HTML-файл, вся логика на vanilla JS, без сборщиков.
- Библиотеки только с CDN (cdnjs), подключай их как classic `<script src="...">` (не как ES-модули `type="module"` и не через `import`), чтобы гарантированно работало на GitHub Pages без сборки.
- Тёмная тема, аккуратная типографика, разделение на вкладки.
- Загрузка новых файлов в любой момент работы (а не только при первом открытии) запускает полный пересчёт всех вкладок, графиков и автовыводов без перезагрузки страницы.
- Все формулы реализованы один раз согласно разделу «Формулы» и переиспользуются во всех вкладках без дублирования логики.
- Нигде в коде нет паттерна «подставить 0, если значения нет» для данных, пришедших из отчёта - только явный статус «нет данных» (см. принцип выше).
- Код с комментариями по ключевым блокам (парсинг, определение типа файла, определение источника себестоимости, расчёт метрик, юнит-экономика, автоинсайты, план-факт, воронка и точки роста, рендер), чтобы можно было дорабатывать самостоятельно.
- Обработка ошибок при загрузке файла с понятным сообщением пользователю, а не молчаливым падением.

### Развёртывание и тестирование (GitHub Pages)

- Файл должен корректно работать именно при открытии по https:// со статического хостинга, без сервера и без шага сборки.
- Учитывай, что localStorage привязан к origin: при тестировании локально через file:// и после деплоя на github.io это разные хранилища - предупреди меня об этом в сопроводительном тексте и посоветуй тестировать сохранение данных именно на итоговом github.io-адресе, а не только локально.
- Добавь на странице небольшую метку версии/времени сборки, чтобы было видно, что открылась именно свежая версия, а не закэшированная браузером.
- В сопроводительном тексте отдельно предупреди, что при переносе кода в файл на GitHub нужно скачать файл целиком, а не копировать текст через интерфейс чата - «умные кавычки» и другие спецсимволы при копировании через чат могут повредить код.

### Формат ответа

Сначала кратко опиши план структуры данных и расчёта метрик (2-3 абзаца). Затем, перед финальным кодом, пройдись по чек-листу и по каждому пункту явно напиши, выполнен он или нет (а если не можешь гарантировать - прямо скажи, в чём риск):
- парсер находит заголовки, даже если они не в первой строке и содержат объединённые ячейки, и корректно приводит числа с запятой/пробелом к числовому виду
- нигде в коде нет «значение || 0» для данных, которые должны быть статусом «нет данных»
- каждая формула (прибыль, маржа, ROI, ДРР, скорость продаж) реализована в одном месте и переиспользуется во всех вкладках
- при нераспознанном типе файла или отсутствующей колонке пользователь видит понятное сообщение с названием файла и колонки, а не пустой экран
- после каждой загрузки виден отчёт о том, что именно распознано (тип, период, строки, ненайденные колонки)
- все библиотеки подключены как classic-скрипты, без ES-модулей
- учтена разница origin между локальным тестированием и GitHub Pages

Затем отдай готовый HTML-файл целиком.
